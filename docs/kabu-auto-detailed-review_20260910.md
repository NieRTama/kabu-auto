## 1. 結論

**私なら、MLの重みや売買閾値の最適化をいったん止め、データの日付、ラベル、検証分割、約定シミュレーションを先に直します。現時点の資料では、MLがルール単独より利益を増やすと判断できません。**

## 4. データと特徴量

### F01：当日足の取得漏れと鮮度検査

`update_symbol()` は `end = date.today()` とし、そのまま `yf.download(..., end=end.isoformat())` に渡します。yfinance公式仕様の `end` は排他的です。したがって営業日Tの16:00に実行しても、このリクエストにはTの足が含まれません。16:20にスキャン時刻をずらすだけでは解消しません。［根拠：S5:23–30・87–93、S16:51–83、E1］

`signal_scan()` は行数を調べますが、その銘柄の最終足が期待する営業日のものか検査していません。データ更新が失敗して古い足しかなくても、新しい生成日時のシグナルとして保存されます。［根拠：S6:346–368、S8:150–158］

私なら、引け後の日足取得はTを含む終了境界に直し、取得後に次を検証します。

1. スキャンの基準日 `as_of_session` を市場カレンダーから確定する。
2. 銘柄ごとに `last_bar_session == as_of_session` を要求する。
3. 遅延配信・休止・欠損を区別し、更新できなかった銘柄は新規候補から外す。
4. `generated_at` と `data_as_of` を別々に保存する。
5. 全体の更新バッチに成功・部分成功・失敗と対象銘柄数を記録する。

単に「今日＋1日」を指定するだけでは、場中の未確定足を拾う場合への対策になりません。引け後の処理契約と足の確定確認をセットにします。上記は修正提案です。

### データ更新とスキャンの依存関係

データ更新16:00、シグナル16:20という別ジョブの登録になっています。完了通知やバッチIDによる連結はなく、20分以内に更新が完了するという時間差に依存しています。［根拠：S16:51–83、S6:162–170・346–368］

私なら「更新完了したバッチをスキャンする」方式にします。更新が20分以上かかった場合や一部銘柄だけ失敗した場合も、スキャンがどのデータ集合を使ったか追跡できる形です。`max_instances` だけで解決する問題ではありません。APSchedulerの同一ジョブの標準同時実行上限は1ですが、別ジョブ間の依存関係までは表しません。［外部根拠：E8］

### 調整済み価格と実際の約定価格を区別する

取得は `auto_adjust=True`、保存時には `adjusted_close` にも同じcloseを書き込んでいます。yfinanceはこの指定でOHLCを調整します。共有DBのスキーマには、取得時点・調整係数・配当・分割イベントの保存項目がありません。［根拠：S5:29–30・50–83、S8:OHLCV定義、E1］

私なら、特徴量に使う調整済み系列と、単元購入・手数料・現金・保有数量に使う価格を分離します。分割は株数と取得原価、配当は現金へ反映する設計にし、同じ企業行動を価格調整と現金で二重計上しないようにします。現在の調整後の過去価格をそのまま当時の100株購入価格とみなす評価は、発注可能性の検証に使わない方針です。

データの取得結果は `dataset_id` で凍結します。同じバックテストを再実行するたびに最新の再調整データへ置き換わると、コード変更による成績差とデータ改訂による成績差を分離できなくなるためです。これはS5の上書き保存に対する設計提案です。

### F06：RSIと日付を落とす処理

`_rsi()` は下落幅の移動平均が0のときNaNに置換します。合成した単調上昇系列では、十分な期間があっても末尾RSIがNaNになることを再現しました。その後、`build_features()` は特徴量がNaNの行を落とします。［根拠：S3:11–16・63–83、V1 `isolated_reproductions`］

さらにラベル生成は、特徴量欠損を落とした後のDataFrameを連番へ変換し、その行数で最大保有日数を数えます。途中に欠落がある場合、「10行先」と「元データの10営業日先」が一致しません。［根拠：S2:142–143］

私なら、RSIは平均損失0・平均利益正なら100、両方0なら50など、端点の扱いを明文化します。特徴量計算では元の日付を保持し、ラベルの時間軸には欠損行を削除する前の市場系列を使います。学習への採否だけをマスクで管理します。テストには上昇のみ、下落のみ、横ばい、途中欠損、出来高0を入れます。

### F07：保存期間と学習期間の違い

週次学習は `load_ohlcv(sym)` を引数なしで呼び、既定の500行だけを読みます。DBに長期履歴があっても、その全量が週次モデルに使われる構造ではありません。一方、バックテストは最大2000行から開始前の単一銘柄データを取って学習します。［根拠：S6:172–189、S5:96–103、S4:63・77–94］

直近500行を使うこと自体は誤りではありません。ただし学習窓は意図して選ぶパラメータにし、`training_window_sessions`、実際の開始・終了日、銘柄ごとの採用件数を保存します。私なら、拡大型と一定期間の移動窓を同じ時系列検証で比較してから選びます。

### 価格単位に依存する特徴量

`ma_cross_sm`、`ma_cross_ml`、`macd`、`macd_hist` は価格差そのものです。複数銘柄を共通モデルに入れると、同程度の相対変化でも株価水準で値が変わります。［根拠：S3:25–31・76–89］

私なら、MA乖離率、MACD/close、MACD/ATRなどへの置換を比較します。これは「木モデルには標準化が必須」という意味ではありません。複数銘柄で特徴の意味を揃えるための変更です。改善したかは期間外成績で判定します。

| 学習記録 | 25件 |
| AUCの記録があるもの | 14件 |
| AUCの範囲 | 0.5035～0.5240 |
| 記録されたAUCの単純平均 | 約0.5112 |
| 直近の学習日時 | 2026-08-31 11:28:25 |

私の評価は、**この記録からMLの有効性は確認できない**です。AUCは順位付けの指標で、ランダムな順位付けの期待値は0.5です。ただし0.5085という一点から「完全に無能力」と断定することもできません。foldごとの予測と正解、日付、銘柄が保存されていないため、適切な信頼区間や局所的な有効性を再計算できません。［根拠：E3、S8:161–174］

accuracy 55.05%には多数派クラスを常に予測するベースラインとの比較が必要です。実際の学習時のクラス比率は、このメトリクス表にありません。例えば正例比率が55%なら常に正例を予測しても55%ですが、これは説明用の仮定であり、このデータの正例比率が55%だったと確認したものではありません。［根拠：S8:161–174、accuracyの定義に基づく例］

Brier lossについても、0.25未満だから採用可能とは判断しません。二値ラベルに常に0.5を予測すれば二乗誤差は0.25です。クラス比率を予測する定数モデルは条件次第でこれより低くなるため、各foldの学習側クラス比率から作ったベースラインと比較します。またBrierは校正だけでなく識別力等も含む指標です。［根拠：E4・E5］

木が1～6本で止まっている点は、調査すべき兆候です。ただし木が少ないこと自体を不良判定にはしません。現在はfoldのearly stopping結果の平均を最終木数にしています。モデル複雑化の前に、正例比率、予測確率の分布、fold別損失曲線、特徴量欠損を見ます。［根拠：S1:145–177、D1］

なお、25件の学習記録は独立した25回の戦略検証ではありません。期間・銘柄が重複し得る再学習の記録です。AUC14件の単純平均は記述統計に限り、これを独立試行の平均として有意性検定することは提案しません。［根拠：D1、S6:172–189］

### F02・F03：時系列CVを組み直す

共有コードは銘柄ごとに特徴量を作る点までは分離できていますが、その後に `ignore_index=True` で連結し、時間と銘柄の識別情報を失います。その連結行に `TimeSeriesSplit(n_splits=5)` を適用しています。［根拠：S1:102–141］

例えばA銘柄の2024～2026年の後にB銘柄の2024～2026年を並べると、学習側にAの2026年、検証側にBの2024年が入る分割が成立します。これは本コードの連結方式を示す例です。`TimeSeriesSplit` は時間順に並んだ入力を前提にしており、銘柄ブロックを自動的にカレンダー順へ直しません。［根拠：S1:118–136、E2］

日付順へ並べ直すだけでも不十分です。ラベルには最大保有期間の未来価格が含まれるのに、分割にはgapもイベント区間の除外もありません。検証開始日の直前の学習ラベルが、検証期間の価格に依存する場合があります。サンプル一意性の重みは、この学習・検証間の重複を除去する仕組みではありません。［根拠：S2:55–75・80–101、S1:136–160］

私なら学習データに次の列を残します。

| 列 | 役割 |
|---|---|
| `symbol` | 対象銘柄 |
| `feature_as_of` | 特徴量に使った情報の最終時点 |
| `decision_at` | 売買判断の時点 |
| `entry_at` | 仮定した最初の執行時点 |
| `label_end_at` | ラベル確定に使った最後の時点 |
| `label` / `net_return` | 予測対象 |
| `sample_weight` | 学習用重み |
| `dataset_id` / `feature_version` | 入力の再現用識別子 |

分割はカレンダー上の期間で決め、同じ検証日を全銘柄で揃えます。学習データは、学習締切までに特徴量もラベルも利用可能だったイベントだけに制限します。境界に重なるイベントは除外します。

片方向のwalk-forwardでは、検証後の未来データをそのfoldの学習に入れないため、後方のembargoを機械的に追加する必要はありません。前後両側を学習に使う別の分割を採用する場合は、重複ラベルのpurgeと検証後のembargoを別々に設計します。行数ベースのgapを銘柄混在データへそのまま指定せず、営業日とイベント区間で扱う方針です。

さらに、現在はearly stoppingに使った検証データで、そのまま最終CV指標も計算しています。私なら、外側の未使用評価期間と、内側の木数・閾値選択期間を分けます。校正も内側の時間分割データで行い、最終評価期間を調整に再利用しません。［現状の根拠：S1:147–160、校正用独立データの根拠：E4］

### F05：何を予測させるかを明確にする

現在のラベルは、当日終値をエントリー価格とし、将来の終値がボラティリティ比例の上下バリアに到達するかを判定します。時間切れでは最終リターンが正なら1です。一方、運用退出には固定損切りとブレークイーブン／トレーリングがあり、バックテストの損切りは日中安値で判定します。［根拠：S2:42–75、S7:511–558、S4:117–133］

したがって「ラベル1＝実運用で利益になる確率」とは読めません。時間バリアに達した小幅上昇はコスト後に損失でも1になりますし、終値ベースでは日中のバリア到達を見落とします。最大保有10行というラベルの制約も、引用した運用退出規則とは一致していません。

末尾では `min(i + max_holding, n - 1)` により、十分な未来がなくても時間切れとしてラベルを確定します。今回の合成データでは最大10に対して未来1行しかないサンプルにラベル1が付きました。［根拠：S2:55・69–75、V1］

私なら、最初は一つの実行可能な契約に絞ります。「Tの引け後に判断、T+1に執行、退出規則と最大保有期間を固定、往復コストを控除」です。末尾の未成熟イベントは除外します。ただし未来の上下バリア到達で既に終了が観測できたイベントは、契約に従って採用できます。最大保有期間分を末尾から一律削除する実装は、簡単で保守的な初期案です。

日足で同日に上限・下限の両方へ到達した場合、日足だけでは到達順を復元できません。私なら初期版は不利側先行の仮定と逆側先行の感度分析を併記し、その差が大きい戦略は日中データが揃うまで採用しません。ラベル用とバックテスト用で同じ退出判定関数を使う提案です。

### F08：私ならMLはまず候補の選別に使う

現在の合成は `rule_score * rule_weight + 2 * (p - 0.5) * ml_weight` です。モデルがない、または推論が失敗した場合も、通常のシグナル生成ではルール重みがそのまま残ります。バックテストでモデル学習ができなかった場合はルール重み1.0になります。［根拠：S9:70–97、S4:79–94］
例えばルール0.3、ルール重み0.5なら、ML欠落時の通常シグナルは0.15です。ルール単独バックテストでは0.3となるため、同じ閾値でも売買判断が変わります。これはコード式からの計算例です。

**MLを一時無効化する際、重みを0/1に変えるだけで現在の閾値を維持すると、取引頻度が変わります。** 私なら、現在の運用を勝手に置き換えず、以下を別バージョンとして比較します。

1. 既存の合成戦略。
2. 縮尺を明示したルール単独戦略。
3. ルールで候補を作り、MLで買い見送りや順位を決める戦略。

最初に試すのは3です。ルールが候補とするイベントに対して「この取引はコスト後に採る価値があるか」を学習させます。全日付を機械的に買い／売りへ変換するより、現行ルールへの追加効果を測定しやすいからです。これは本Botに対する私の設計提案で、有効性は未検証です。

分類確率だけで発注する場合も、利益・損失の大きさとコストを揃えます。単純化した期待値は `p × 平均利益 − (1−p) × 平均損失 − コスト` です。利益側と損失側が非対称なら、採用確率の境界が0.5になるとは限りません。これらの推定値も学習期間だけで求めます。

モデル失敗時は「ルール単独の定義済み戦略へ切替」または「新規候補生成を停止」のどちらかを設定として明示します。既存ポジションの退出管理は、候補生成の障害と分離します。

### F04：同じ終値で判断・約定する問題

現行エンジンではTの終値を含む特徴量でスコアを作り、買いも売りもTの終値にコストを加えて約定します。通常運用は引け後スキャンから翌朝の実行です。シグナルを作れる時点と約定できる時点が違います。［根拠：S4:144–192、S6:346–408、S16:75–89］

私ならシミュレーションを、前日までに決まった注文の執行→保有と現金の更新→退出条件の処理→日末評価→次回候補生成の順にします。T終値の情報はT+1以降の注文にだけ使います。

実運用の9:05約定を日足openで正確に再現することはできません。日足しかない段階では「翌営業日寄付を仮定した近似検証」と明記し、実時刻の板・約定モデルの検証とは分けます。採用を判断する段階で、必要な時刻粒度のデータと照合します。

損切りでは、日中安値が損切り線以下なら損切り線で約定します。寄付から線を下回る場合も同じ扱いです。例えば100で購入、損切り95、翌日open90という合成ケースでは95約定を仮定できません。通常の売りストップの近似なら `min(open, stop)` を出発点とし、値幅制限や売買停止などで退出できない条件を別に扱います。［根拠：S4:117–125、コード経路に対する例］

### 運用と共通化する対象

現行バックテストは単一銘柄の現金・数量を保持し、退出は固定損切り、シグナル売り、期間末決済です。運用側のブレークイーブンとトレーリング、および複数銘柄の資金競合を同じ条件で検証するエンジンにはなっていません。MLも開始前に一度だけ学習し、テスト期間中には再学習しません。［根拠：S4:77–214、S7:511–558、S6:172–189］
私なら、戦略判断・退出・資金配分の純粋関数を共通化し、執行アダプターを差し替える構成へ進めます。まず日足のポートフォリオ検証を作り、銘柄の選択順、資金上限、セクター上限、未約定予約、追加購入を含めます。指値については注文価格と高安の関係だけで約定確実とせず、未約定・部分約定・出来高制約を仮定として明示します。

現行paperは16:20のスキャン中にDB終値で即時売買し、場中のpaper損切りも日足終値を参照します。したがってpaperで動いたことだけを、翌朝の市場執行や日中退出の検証完了とは扱いません。［根拠：S6:305–320・346–398］

バックテスト内の推論例外は `except Exception: pass` で黙って無視されます。私なら1件でも発生した実行には `degraded=true` と失敗数を付け、比較・モデル昇格から除外します。研究用途では失敗時に実行自体を止める方が原因を追いやすいです。［根拠：S4:154–163・253］

### 再現用に保存する実行条件

現行 `BacktestRun` には閾値とコスト等はありますが、全設定、モデルID、データID、コード版を記録する項目がありません。実行時には変更可能な現在設定から損切り率・資金配分率・重みを読んでいます。［根拠：S4:50–60・235–258、S8:177以降のBacktestRun定義］

私なら、開始時に全設定を不変のスナップショットとして取得し、`run_id / strategy_version / config_hash / dataset_id / model_id / code_version / execution_model_version` を保存します。結果は最終リターンだけでなく、日次NAV、保有、注文候補、除外理由、予測確率まで辿れる形にします。

## 7. 運用・設定・セキュリティで直したい点

### F10：価格が取れたことと、新しい価格が取れたことを区別する

リスク計算の現在値取得に失敗するとDB終値で補完し、返り値は銘柄→価格だけです。DB終値にも日付が付いて返りません。価格が存在すれば含み損益計算へ進むため、過去価格による評価とリアルタイム評価を下流で区別できません。［根拠：S7:115–126・179–209、S5:122–143］

私なら `PriceQuote(value, observed_at, source, session, quality)` を返します。表示用途には古い価格とその日付を出してもよいですが、新規リスク追加の判断には鮮度条件を設けます。価格が不明な保有を0損失として安全扱いしない設計です。既存リスクを減らす操作まで一律に停止する提案ではありません。

銘柄上限の分母は現在 `cash_balance − reserved` に比率を掛けています。これは総資産比率ではなく残余力に対する枠であり、ソースの説明もそうなっています。設計選択なので即バグとはしませんが、設定の「1銘柄あたり最大資金比率」と解釈がずれやすい点です。私なら「資産全体に対する集中上限」と「今回の注文へ割り当てる現金上限」を別項目にします。［根拠：S7:353–413、`config.yaml`:16］

### F11：アクティブなプロファイルの上書き

`update_custom()` は更新対象がアクティブなら `_apply()` しますが、`import_profile(..., overwrite=True)` は同じチェックをせず保存だけします。アクティブな同名プロファイルを取り込むと、保存した内容と実行中設定が一致しなくなる経路です。［根拠：S10:271–285・323–336］

私なら更新・import・切替を一つの適用関数に通します。検証済みの設定を一時ファイルへ書き、置換成功後に実行中設定を一括更新します。現状の `_apply()` は共有辞書を項目ごとに変更し、`set_active()` は適用後に永続化するので、保存失敗時や並行読取時の整合も見直します。［根拠：S10:145–155・204–210・226–240］

取引判断側は評価開始時に同じ `config_version` を固定し、途中のGUI変更で一つの注文だけ新旧設定が混ざらないようにします。起動時の全体設定にも、型・有限値・範囲・重み合計・閾値関係を検証するスキーマを設けます。プロファイルの7項目には検証が既にありますが、全体設定のloadはYAML読込と環境変数上書きが中心です。［根拠：S10:49–113、S15:11–24］

### F12：初期設定を先に行った人が利用者になれる

`/api/setup` は認証除外パスで、ハンドラー自体もセットアップ用トークンや接続元の確認をしません。認証未登録なら渡された認証情報を作成します。LANから到達できる初回起動では、先にこのAPIを呼べる第三者がアカウントを作成する経路があります。また認証ファイルの読込失敗を `_data=None` として扱うため、破損等でも未設定状態へ戻ります。［根拠：S11:182–211・347–354、S12:32–54・62–90］

これは認証済み状態を常時突破できるという意味ではありません。**未設定または読込失敗、かつ第三者からAPIへ到達可能**という条件付きの問題です。

私なら、初回設定をローカル操作へ限定するか、コンソールに一度だけ出す短命のセットアップ資格情報を必須にします。「未作成」と「存在するが壊れている」を分け、後者は認証を閉じたまま修復を要求します。任意の新規登録へ戻しません。

### F13：ログアウトとAPIトークン認証

ミドルウェアは `kabu_session` または `kabu_token` Cookieを認証として認めますが、ログアウトは前者だけを破棄します。過去にクエリトークンで発行した `kabu_token` があれば、そのCookieによる認証は継続可能です。［根拠：S11:90–93・185–214・222–238・378–384］

私ならブラウザは失効可能なセッションだけに揃え、プログラム向けAPIトークンはヘッダー限定にします。URLのクエリトークンは受け付けません。リダイレクトでURLを清掃しても、最初のリクエストを受けたアクセスログ等への流出を取り消すことはできません。［根拠：E9、S11:222–238］

LAN待受設定は `0.0.0.0`、Cookie Secureはfalseです。実際にHTTPS終端やVPNがあるかは資料から確認できません。LAN経由で使うなら、その経路を確認し、HTTPSを使う構成ではSecureを有効にします。Cookie認証の状態変更操作にはOrigin検査とCSRF対策を加える提案です。SameSite=StrictとHttpOnlyは既に付いているので、その点は維持します。［根拠：`config.yaml`:173–188、S11:340–344、E10・E11］

認証ハッシュはPBKDF2-HMAC-SHA256の20万回です。OWASP掲載の同方式の推奨は60万回なので、端末上の認証時間を測った上で強化し、次回の成功ログインで更新する案を勧めます。認証ファイルの「ハッシュだから復元できない」という説明は、辞書照合による推測まで防げる意味にはしないよう修正します。［根拠：S12:22–25・93–104、E12］

### F14：今回消したWebhookが再びログへ出る経路

`alerts._send_one()` のコメントは秘密情報を出さないと説明していますが、実装は `last_error` をそのまま文字列化しています。通知失敗の例外にWebhook URLが含まれれば再びログへ残る経路です。ロガーの `diagnose=False` は変数展開を抑えますが、この明示的な例外文字列の出力は除去しません。［根拠：S13:104–120、S14:192–241、今回の伏字化対象ログ］

私なら、通知失敗はプロバイダー名・例外型・HTTPステータス・再試行回数・相関IDを基本にし、メッセージが必要なら共通のマスキングを通します。フルURL、相対パス、ヘッダー、入れ子の例外をテスト対象にします。ログだけでなく、例外を保存するDB列や通知本文も同じ境界で処理します。［設計上の根拠：E13］

### F15：永続化とモデルの来歴

`Trade.intent_id`、`OrderApproval.intent_id`、`Fill.broker_order_id` は整数列ですが、外部キー宣言はありません。DB初期化はWALを設定する一方、接続ごとのforeign_keys有効化がありません。DBファイルのintegrity_checkがokでも、これら業務上の紐付けが正しいことまで検査した結果ではありません。［根拠：S8:60–130・346–362、V1、E14］

私なら外部キー、数量・残数量の制約、イベント重複検知を段階的に加えます。既存DBに制約を加える前に不整合を抽出し、既存スキーマからの移行・再実行・復元をテストします。FIFO不足時の損益未計上といった台帳処理は、別途対応済みの範囲と照合してから残件にします。今回の分析だけで本体の移行は行っていません。

モデルはpickleと隣接JSONのハッシュで管理されています。ハッシュ不一致を拒否する実装はありますが、両ファイルを同時に置換できる相手に対する真正性の保証にはなりません。Python公式も信頼できないpickleのロードを警告しています。私ならLightGBMのモデル保存形式とJSONメタデータにし、配布元・ファイル権限を管理します。署名が必要な運用なら検証鍵をモデルと別の信頼境界に置きます。［根拠：S1:44–62・180–186・225–280、E6・E7］

加えて `model_id`、学習窓、銘柄集合、ラベル版、特徴量版、クラス比率、各foldの結果、コード版、依存関係版、データIDを保存します。現在のモデルメタには特徴量一覧・LightGBM版・accuracy等がありますが、これらすべてを再現できる情報はありません。［根拠：S1:44–62］

shadow運用では、同じ入力に対して現行と候補の判断を並行して記録し、候補は発注へ接続しません。現行との差が何によって生じたか、見送った候補の結果も含めて記録します。

### 段階F：設定・認証・ログの整合を仕上げる

F11～F15はML評価と独立して修正できます。初期設定の保護、ログアウトの整合、ログマスキング、プロファイル適用の原子性を先に扱い、その後にDB制約・監査メタデータへ進みます。

テスト数そのものを目標にせず、既存テストへ不足する振る舞いを追加します。共有から除外されたテストが既に該当ケースを含む場合は、その期待値と実装を照合します。

## 9. MLの採用判断に使う評価設計

以下は私が提案する評価契約です。固定の数字だけで採用を決める基準ではありません。

### 比較条件

| 比較対象 | 確認したいこと |
|---|---|
| 現金維持 | 売買すること自体の価値 |
| 投資対象に対応した保有ベンチマーク | 単に市場上昇へ乗った効果との差 |
| ルール単独 | MLなしの基準成績 |
| 既存合成 | 現在の判断方式の再現 |
| ルール候補＋ML選別 | MLの追加価値 |
| ML単独 | 必要な場合に限り、ルールとの役割分担を調べる補助実験 |

ベンチマークも配当・分割・現金比率・コストの扱いを揃えます。異なる期間、異なる資金、異なる投資対象のリターンを直接比較しない設計です。

### 機械学習として記録するもの

- fold別・銘柄別・期間別の件数、正例率、除外件数。
- ROC-AUC、PR系指標、log loss、Brierと定数モデルとの差。
- 予測確率のヒストグラムと校正曲線。校正は独立した過去期間で学習。
- 取引に採用する上位群のコスト後成績。全体AUCだけで判断しない。
- 重要特徴の安定性。学習内の分割回数だけで有効と結論しない。
- 予測・ラベル・日時・銘柄を含む期間外予測明細。

指標の意味と校正方法はE3～E5を参照。上の記録項目の選択は本レビューの提案です。

### 売買システムとして記録するもの

- コスト後の累積利益、日次NAV、最大DD、取引回数、保有期間、資金使用率。
- 勝率と平均利益・平均損失、期待損益、損益の裾の損失。
- ルール単独に対する追加損益。取引を減らしただけかも分けて見る。
- 銘柄・業種・相場期間ごとの利益寄与と集中。
- 指値未約定、資金不足、流動性除外、モデル失敗の件数。
- 注文想定時刻、約定仮定、コスト仮定の変更に対する感度。

私なら、通常コストと不利なコスト条件、ギャップ損失、未約定率上昇を組み合わせて再評価します。例えば通常コストの2倍はストレスシナリオの候補であり、実際の市場コストが必ず2倍になるという主張ではありません。

### 不確実性と合格条件

同じ日の複数銘柄や重複保有イベントを独立サンプルとして扱わず、日付のまとまりを保つ再標本化等で成績差の不確実性を確認する方針です。方法・ブロック長・比較回数を事前に記録します。今回の集計済みDBだけでは、その信頼区間を新たに算出できません。

昇格には、少なくとも次を要求します。

1. 時系列リーク、データ鮮度、ラベル成熟の検査を通過している。
2. ルール単独に対する追加効果が、未使用期間でコスト後に確認できる。
3. 利益が特定の1銘柄・1期間だけに依存していない。
4. 最大DD等が、ユーザーの事前に決めたリスク予算内に収まる。
5. コストや執行仮定を多少厳しくしても、採用理由が消えない。
6. shadowで入力品質、判断差、障害時動作を確認できる。

「AUCが0.55を超えれば採用」「paperを1か月動かせば合格」といった一律基準は、私なら置きません。売買回数が少なければ期間を長くし、比較の不確実性が大きければ昇格を保留します。利益目標、許容DD、学習窓などの最終値は、ユーザーの資金と運用目的に依存する未確定事項です。

## 10. 既存テストへ追加・確認したいケース

テスト一式は共有対象外なので、以下は「存在しないテスト」の一覧ではなく、修正時に確認したいケースです。

| 領域 | ケース | 期待する結果 |
|---|---|---|
| 日足 | 引け後のT日更新 | T日を含む取得範囲で、最終足もT日 |
| 日足 | 更新失敗・一部銘柄だけ古い | 古い足を当日の新規候補へ混ぜない |
| 特徴量 | 上昇のみ・下落のみ・横ばい | 仕様どおりのRSI端点、予期しない全行脱落なし |
| 特徴量 | 将来行を追加 | 過去特徴が変わらない |
| ラベル | 最大保有10、未来1行、バリア未到達 | 未成熟として学習対象外 |
| ラベル | 途中欠損・上下同時到達 | 日付と採用ポリシーが一貫 |
| 分割 | A/Bの同一期間を連結 | 全銘柄で時間境界が共通、未来学習なし |
| 分割 | 学習末尾ラベルが検証へ重なる | 該当イベントをpurge |
| 評価 | 外側テストの値を変更 | 学習済みモデル・内側で選んだ閾値が変わらない |
| 約定 | T終値で買い条件成立 | T+1以降にのみ新規約定 |
| 損切り | 寄付が損切り線より下 | 損切り線での楽観的約定をしない |
| 資金 | 同日に複数銘柄が候補 | 現金・予約・集中上限を共有して判定 |
| 再学習 | 候補モデルが成績悪化 | 現行を自動上書きしない |
| 推論 | 例外・特徴量不一致 | 設定済みの代替動作と失敗記録 |
| プロファイル | アクティブ名へimport上書き | 保存値・実行中設定・表示が一致 |
| 永続化 | ディスク書込失敗 | 旧設定が利用可能で、新旧が混在しない |
| 認証 | authファイル破損 | 未認証setupが再開しない |
| ログアウト | トークンCookie保持でログアウト | ブラウザの認証が意図どおり失効 |
| 秘密情報 | URL付き・相対パス付き例外 | ログ・DB・通知に実トークンを残さない |
| DB移行 | 旧DB・再実行・復元 | 重複適用・孤立レコード・数量不整合を検知 |
