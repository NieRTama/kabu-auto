## 1. 背景と目的

kabu-autoは49モジュール・151本の内部importを持ち、設計書は2957行に達している。
現状ObsidianのvaultにはドキュメントMarkdownが11個あるが、相互リンク（wikilink）が
実質ゼロのため、**グラフビューを開いても孤立した点が11個並ぶだけ**で機能していない。

目的は「どのファイルが何をしていて、誰に使われ、どの設計判断・事故に関係するか」を
グラフとして辿れるようにすること。

## 2. 決定事項（ユーザー承認済み）

| # | 論点 | 決定 |
|---|------|------|
| 1 | グラフのノードにするもの | **モジュール＋ドキュメント＋節を統合** |
| 2 | 節ノートと原本の関係 | **スタブ方式**（要約とリンクのみ。本文は原本に残し重複ゼロ） |
| 3 | 生成物の置き場所 | **vault専用**。gitはスクリプトのみ追跡（生成物は派生データ） |
| 4 | 再生成のタイミング | **push時のvault同期手順に組み込む**（常駐プロセスには足さない） |
| 5 | 実装アプローチ | **案3: 完全自動生成のみ。手動オーバーライド表は作らない** |
| 6 | 記号名による照合 | **採用**（計画時の実測で追加）。設計書はモジュールをパスでなく記号名で書くため、パス走査だけでは辺47本・繋がる節29/71件に留まる。`ast`でクラス／関数名を取る完全機械的な手法で辺225本・48/71件へ |

### 2.1 案3を選んだ理由

手動の対応表（`graph_overrides.yaml` 等）を持つと、設計書という原本があるのに
その外側に第二の真実が生まれ、コード変更のたびに更新漏れが起きる。
まず自動生成のみで作り、**実際に孤立ノードが実害になるか測ってから**判断する。
もし辺が足りなければ、対応表を足すより**設計書側にモジュールパスを1行書く**方が
原本が正確になり筋が良い、という選択肢を残す。

## 4. データモデル

### 4.1 ノードの種類

| 種類 | 個数 | 実体 | 生成 |
|------|------|------|------|
| モジュール | 49 | `src/**/*.py` + `main.py` | する |
| 節 | 71 | 対象ドキュメントの `##` 見出し | する |
| ドキュメント | 11 | vault内の既存Markdown | **しない**（既存ファイルがそのままノード） |

`__init__.py` は除外する（役割を持たないため）。

### 4.2 辺の種類と抽出元（すべて機械的に導出）

| 辺 | 抽出元 | 実測 |
|----|--------|------|
| モジュール → モジュール | `ast` によるimport解析 | 151本 |
| モジュール → 解説節（アンカー） | `### N.N <path> — <役割>` 見出し（型A） | 29本 |
| 節 → モジュール（パス） | `##` 節本文中の `src/xxx/yyy.py` 表記 | 47本 |
| 節 → モジュール（記号名） | 節本文中のクラス／関数名（`ast`で抽出・曖昧名は除去） | 計225本 |
| 節 → 原本ドキュメント | 見出しの所属元 | 全節 |

節スタブは必ず原本ドキュメントへのリンクを持つため、**モジュール言及が無い節も孤立しない**。

### 4.3 `###` 見出しの4つの型（実装上の注意）

`###` 見出しのうちモジュールパスを含むものは41件あるが、**役割の供給源として使えるのは
型Aの29件だけ**である。残り12件は事故節の小見出しにパスが出ているだけで、
「そのモジュールの解説節」ではない。

| 型 | 件数 | 例 | 扱い |
|----|------|-----|------|
| **A** | 29 | `### 1.1 src/core/config.py — 設定管理` | **役割として採用**。解説節アンカーにもする |
| B | 10 | `### 1.18.3 FIFOロット台帳（src/execution/lots.py）` | 採用しない |
| C | 1 | `### 1.24.6 src/core/discord_bot.py / discord_queries.py — …` | 採用しない（パス2個で区切りが `/`） |
| D | 1 | `### 1.33.4 通知の判断は \`src/core/broker_watch.py\` へ分離` | 採用しない |

型B・C・Dのパスは、親の `##` 節を本文走査する際に**節→モジュールの辺として拾われる**ため
情報は失われない。型Aだけを狙う正規表現にすることで、事故節の小見出しを
「モジュールの解説」と誤って扱うことを防ぐ。

## 6. 出力仕様

### 6.0 用語の定義

本章以降で使う導出値を先に定義する。

| 用語 | 定義 | 例 |
|------|------|-----|
| **レイヤ名** | モジュールパスの `src/` 直下のディレクトリ名。`main.py` は `root` とする | `src/risk/manager.py` → `risk`<br>`src/core/config.py` → `core`<br>`main.py` → `root` |
| **ドキュメント略称** | 元ファイルの拡張子を除いたファイル名（basename stem） | `docs/詳細設計書.md` → `詳細設計書`<br>`README.md` → `README` |
| **節番号** | `##` 見出し先頭の数字とドットの並び。無ければ空文字 | `## 1.40 含み損益...` → `1.40`<br>`## 主な機能` → （空） |

レイヤ名は11種類になる: `analytics` / `api` / `backtest` / `core` / `dashboard` /
`data` / `execution` / `risk` / `services` / `strategy` / `root`。
これがグラフの色分け（`layer/*` タグ）の単位になる。

### 6.1 ファイル名規則

**モジュールノート**: `src.` を除いたドット表記。

| 元 | 生成先 |
|----|--------|
| `src/core/config.py` | `modules/core.config.md` |
| `src/risk/manager.py` | `modules/risk.manager.md` |
| `src/execution/order_manager.py` | `modules/execution.order_manager.md` |
| `main.py` | `modules/main.md` |

**節スタブ**: `<ドキュメント略称>-<節番号>-<短縮タイトル>.md`

`docs/詳細設計書.md` の `## 1.40 含み損益がOHLCV終値ベースで、実勢と大きく乖離していた（2026-09-09）`
は `sections/詳細設計書-1.40-含み損益がOHLCV終値ベースで、実勢と大き.md` になる。

- 短縮タイトルは節番号を除いた見出しテキストを **24文字** で切る
- Windowsで使えない文字（バックスラッシュ、スラッシュ、コロン、アスタリスク、
  クエスチョン、ダブルクオート、不等号、パイプ）は `-` に置換する
- 節番号が無い見出し（`## 主な機能` 等）は番号部分を省く

### 6.2 モジュールノートの構成

frontmatter に `tags: [kabu-auto/module, layer/<レイヤ名>]`、`module: <元のパス>`、
`generated_by: gen_graph_notes.py` を持つ。本文は次の順で構成する。

1. 見出し（ノート名と同じ。例 `# risk.manager`）
2. `**役割**: リスク管理`
3. モジュールdocstringの先頭段落を引用ブロックで（最大3行）
4. `## 依存先（このモジュールが使う）` — wikilinkの箇条書き
5. `## 依存元（このモジュールを使う）` — wikilinkの箇条書き
6. `## 解説` — `[[詳細設計書#1.10 src/risk/manager.py — リスク管理]]` 形式のアンカーリンク
7. `## 関係する設計判断・事故` — 該当する節スタブへのwikilink

補足規則:

- `**役割**` は次の3段フォールバックで決める（実測: 29件 / 20件 / 1件）
  1. `### N.N <path> — <役割>` 見出し（型A）の `—` 以降
  2. 無ければモジュールdocstringの先頭行
  3. docstringも無ければ `（説明なし）`（実測で該当は `src/core/logger.py` の1件のみ）
- 依存先・依存元・解説・関係する節が空のセクションは**見出しごと省略**する
- 依存元は依存先グラフを反転して算出する

### 6.3 節スタブの構成

frontmatter に `tags: [kabu-auto/section, kabu-auto/<ドキュメント略称>]`、
`source: <元のパス>`、`generated_by: gen_graph_notes.py` を持つ。本文は次の順。

1. 見出し（節見出しのテキストそのまま）
2. 本文冒頭の抜粋（最大3行・200文字）
3. `## 本文` — 原本へのアンカーリンク `[[詳細設計書#1.40 ...]]`
4. `## 関係するモジュール` — wikilinkの箇条書き

補足規則:

- 冒頭抜粋は、見出し直後の最初の非空行から取る
- 表・コードブロック・引用の行（パイプ始まり、バッククオート3連始まり、
  大なり記号始まり）は抜粋対象から除外し、次の散文行を探す
- 「関係するモジュール」が空なら見出しごと省略

### 6.4 index.md

生成日時・件数のサマリと、Obsidianのグラフ色分け設定（コピペ用JSON）を載せる。
**生成日時を書くのはこのファイルだけ**（6.5および7.1参照）。

### 6.5 生成日時を各ノートに書かない理由

モジュールノート・節スタブに生成日時を書くと、内容が実質同じでも毎回全ファイルの
バイト列が変わり、iCloudが120ファイルを再同期し続ける。日時は `index.md` に限定する。

## 7. 生成アルゴリズム

### 手順

1. **モジュール収集**
   - `src/**/*.py`（`__init__.py` 除く）と `main.py` を列挙
   - 各ファイルを `ast.parse` し、`Import` / `ImportFrom` ノードを `ast.walk` で全て拾う
     （**関数内importが実在するため walk が必須**。`main.py:204`、`src/dashboard/app.py:393` 等）
   - 依存解決は7.2の規則による
   - 自己参照・`src` 配下以外・相対importは捨てる
   - モジュールdocstringを `ast.get_docstring` で取得

2. **役割見出しの収集**
   - `docs/詳細設計書.md` から次の正規表現で抽出し、
     `{モジュールパス: (節番号, 役割, 見出し全文)}` を作る

   ```
   ^###\s*([\d.]+)\s+(src/[\w/]+\.py|main\.py)\s*[—–-]\s*(.+)$
   ```

3. **節の収集**
   - 対象4ドキュメントを `^## ` で分割
   - 各節から `src/xxx/yyy.py` 形式のパス言及を集合で抽出
   - 冒頭抜粋を作る（6.3の規則）

4. **逆引きの構築**
   - モジュール依存グラフを反転して「依存元」を作る
   - 節→モジュールを反転して「モジュール→関係する節」を作る

5. **出力**
   - 全ノートをメモリ上で組み立てる
   - 出力先の衝突検査（8.2）→ 問題があれば**何も書かずに中断**
   - ファイル書き出し（UTF-8・BOM無し・改行LF）
   - 陳腐化ファイルの削除（8.1）
   - `index.md` を書く

### 7.1 決定性（重要）

同じ入力からは**バイト単位で同一の出力**を出すこと。

- リスト（依存先・依存元・関係する節）はすべて**ソートしてから**出力する
- モジュールノート・節スタブに生成日時を書かない（6.5）

### 7.2 import解決の規則

| 記述 | 解決先 |
|------|--------|
| `import src.a.b` | `src.a.b` |
| `from src.a.b import X` | `src.a.b`（`src/a/b.py` が実在するため） |
| `from src.a import b` | `src/a/b.py` が存在すれば `src.a.b`、無ければ `src.a` |

`from src.core import preflight` は `src/core/preflight.py` が実在するので
`src.core.preflight` へ、`from src.data.database import Position` は
`src.data.database` へ解決される。**この分岐はテストで固定する**（9章）。

## 8. 安全性要件

### 8.1 陳腐化ファイルの削除

モジュールを削除・改名したとき、対応するノートが残り続けるとグラフが実態とずれる。
生成後、出力ディレクトリ配下で今回生成しなかった `.md` を削除する。

**ただし frontmatter に `generated_by: gen_graph_notes.py` を持つファイルのみ削除する。**
ユーザーが `graph/` に手書きノートを置いた場合に消さないため。

### 8.2 ファイル名衝突の検査

Obsidianのwikilinkはノート名で解決するため、vault内で名前が重複するとリンクが
意図しない先に繋がる。生成前に以下を検査し、1件でもあれば**何も書かずに中断**する。

- 生成ノート同士の名前重複
- 生成ノート名と、`graph/` の外にある既存vaultノート名の重複

中断時は、衝突したノート名と既存ファイルのパスを表示する。

### 8.3 エンコーディング

Windows環境でcp932起因の失敗が頻発しているため明示する。

- ファイル読み書きは必ず `encoding="utf-8"` を指定する
- 書き出しは `newline="\n"`（CRLF混入を防ぐ）
- BOMは付けない
- スクリプト自身の標準出力も UTF-8 にする（`sys.stdout.reconfigure(encoding="utf-8")`）

### 8.4 wikilinkの誤生成の抑止

docstringや本文抜粋に `Callable[[list[str]], dict[str, float]]` のような型注釈が
含まれると、Obsidianが `[[list[str]]` をwikilinkと誤認識する
（実際に `詳細設計書.md` で発生している）。

抜粋テキスト中の連続する角括弧開きは、バックスラッシュでエスケープしてから書き出す。

### 8.5 出力先の引数化

既定の出力先はvaultだが、テストが実vaultを破壊しないよう**必ず差し替え可能**にする。

| コマンド | 動作 |
|----------|------|
| `python scripts/gen_graph_notes.py` | 既定のvaultへ出力 |
| `python scripts/gen_graph_notes.py --out <dir>` | 出力先を差し替え |
| `python scripts/gen_graph_notes.py --dry-run` | 書かずに件数と衝突のみ報告 |

既定パス（機械固有のため定数としてファイル先頭に置く）:

```
C:\Users\garnet\iCloudDrive\iCloud~md~obsidian\Tama vault\Claude\graph
```

出力先の**親ディレクトリが存在しない場合は中断**する。iCloudがオフラインのときに
ローカルディレクトリを勝手に作り、同期されない場所へ書くのを防ぐため。

## 9. テスト要件

`tests/test_gen_graph_notes.py`。**実vaultには一切書かない**（`--out` に `tmp_path` を渡す）。

| 観点 | 内容 |
|------|------|
| import解析 | フィクスチャのモジュール木から期待どおりの辺が出る |
| 関数内import | 関数の中に書かれた `from src.x import y` も辺として拾う（回帰防止） |
| import解決 | `from src.a import b` が、`src/a/b.py` の有無で `src.a.b` / `src.a` に正しく分かれる |
| 役割抽出 | `### 1.10 src/risk/manager.py — リスク管理` から役割「リスク管理」が取れる |
| 役割の代替 | 見出しが無いモジュール（`main.py`）はdocstring先頭行が役割になる |
| 逆引き | Aを使うのがBとCなら、Aのノートの依存元にB・Cが両方載る |
| ファイル名 | 禁止文字を含む見出しが安全な名前に変換される |
| 衝突検査 | 名前が重複する状況で、**何も書かずに**中断する |
| 陳腐化削除 | `generated_by` を持つ古いファイルは消え、持たない手書きファイルは**残る** |
| 決定性 | 2回実行してバイト単位で同一（`index.md` を除く） |
| wikilinkエスケープ | `list[str]` を含むdocstringから `[[` が生成されない |
| 空セクション | 依存元が無いモジュールのノートに空の見出しが残らない |

既存の1066件のテストを壊さないこと。

## 10. 運用手順への組み込み

「しこみっぷ」（試験→修正→コミット&プッシュ）の後段に1ステップ追加する。

1. 試験
2. 問題あれば修正
3. コミット & プッシュ
4. vaultへドキュメント同期（既存）
5. `python scripts/gen_graph_notes.py` ← **追加**

あわせて記憶ファイル `obsidian_vault_sync.md` に手順5を追記する。

## 12. 実装後に測ること（案3の第二段階）

生成後、以下を測ってユーザーに報告する。判断はその数字を見てから行う。

- モジュール言及を持たない節スタブの件数（辺がドキュメントへの1本だけのもの）
