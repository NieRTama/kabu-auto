## 1. 目的

現状、MLが利益に寄与しているかを**判定できない**。保存済みAUCは0.5085だが、
その数値が意味を持つための前提（時系列の分離、データの鮮度、ラベルの定義、
判断時点と執行時点の分離）が揃っていないため、良い数字が出ても運用への
再現性を評価できない。

本設計の目的は「MLを効かせること」ではなく、**MLが効いているかを測れる状態を作ること**である。
効果測定はこの基盤が入ってから行う。

## 3. 設計方針

F04（同一終値で判定・約定）とF05（ラベルが運用規則と不一致）は別々の欠陥に見えるが、
根は一つである。「売買判断 → 執行 → 退出」の規則が、ラベル生成・バックテスト・実運用の
3箇所に別々の実装として散らばっており、片方を直しても他方とずれる。

したがって**判断の規則を1箇所に集約する**設計を採る。ただし**約定はそこに含めない**。
判断と約定を同じ関数が返すと、将来の日足をまとめて受け取る関数が過去検証専用になり、
その時点までの足しか渡せない実運用のインターフェースにならないためである。

個別修正（既存モジュールのin-place改修）は工数では有利だが、直した直後は一致していても
次に退出条件を触った時に静かにずれるため採らない。検証系を完全に別パッケージへ分離する案も、
運用と検証が別実装になり「バックテストで良かったものが運用で再現しない」という問題そのものを
再生産するため採らない。

### 3層の責務

| 層 | 入力 | 出力 |
|---|---|---|
| 退出ポリシー（`policy.py`） | 現在の保有状態、その時点で観測できる価格・スコア、固定設定 | 次の状態、退出意図、発動理由 |
| 過去検証アダプタ（`execution.py`） | 退出意図、注文条件、利用可能な日足 | 仮定に基づく約定・未約定・部分約定 |
| 実運用アダプタ | 退出意図、実際の市場情報 | 注文の実行と証券会社から確認した約定 |

ラベル生成とバックテストは**同じ過去検証アダプタ**でポリシーを逐次駆動する。
実運用アダプタの導入は段階E（shadow）まで行わない。§10の切替表を参照。

各モジュールの依存:

| モジュール | 何をするか | 何に依存するか |
|---|---|---|
| `policy.py` | 保有状態の遷移と退出意図の生成 | 設定のみ（DB・ネットワーク・将来足に触らない） |
| `execution.py` | 退出意図・エントリー意図を約定へ変換し、コストを一元的に控除する | `policy.py` |
| `dataset.py` | イベント表の生成・保存・`dataset_id` の払い出し | `policy.py` `execution.py` `indicators.py` `market_data.py` |
| `validation.py` | 日付境界でのfold分割、purge、入れ子CV、予測明細の収集 | `dataset.py` |
| `portfolio.py` | 現金・保有・セクター上限・銘柄間の資金競合 | なし（純粋な状態機械） |
| `walkforward.py` | 日次ループの進行と再学習スケジュール | 上記すべて |

`dataset.py` はコスト控除後のラベルを作るため `execution.py` に依存する。
したがって**執行アダプタの最小部分は段階Bと同時に必要**である（§13の実施順を参照）。

## 5. 段階A: データ土台（F01・R4・R5）

> **実装済み（2026-09-12）。** 本節は設計時点の記述であり、以下の「現行実装は〜」
> という指摘は**すべて段階Aで解消されている**。実装は
> `docs/superpowers/plans/2026-09-10-ml-evaluation-stage-a.md` と、
> `feature/ml-eval-stage-a` をマージしたコミット群（`5e85976`〜`e9b1999`）を参照。

### 取得境界

`fetch_ohlcv` に渡す `end` を `end + 1日` にする。yfinance公式仕様の `end` は排他境界であり、
現行実装は営業日Tの引け後に実行してもTの足を取得できない。

**境界の解釈は1箇所に固定する。** 引数 `end` を「含む」とし、排他への変換は
`fetch_ohlcv` の内部だけで行う。呼び出し側では一切加減算しない。
内部と呼び出し側の双方で1日足す事故を防ぐためである。

### 生値と調整値の分離（R4）

`ohlcv` テーブルは既に `close` と `adjusted_close` の2列を持つが、
設計時点では `auto_adjust=True` で取得した調整値を両方へ書いていた。

取得を `auto_adjust=False` に変え、**生のOHLCを `open/high/low/close` へ、
調整済み終値を `adjusted_close` へ**入れる。スキーマ変更は不要である。

用途を分ける。

| 用途 | 使う価格 |
|---|---|
| 特徴量・リターン計算 | 調整済み系列 |
| 株数・単元・必要資金・現金 | 生値 |

これを分けないと、1対2分割で過去価格が半値に調整された銘柄について
「当時100株買えたか」の判定が変わる。分割で株数と価格が整合し、
**分割だけでは評価額・現金・損益が増えない**ことを最小テストで固定する。

**分割・併合の比率は価格系列から導出しない。** Yahooの生の終値（`auto_adjust=False`）は
分割については既に調整済みで、`Adj Close` が追加で配当調整を行うため、
生値と調整値の比の変化は配当しか表さない。`yfinance.Ticker.splits` が返す
分割イベントそのものを唯一の権威とし、新テーブル `CorporateAction` に保存する。

配当は現金として扱い、調整価格と二重計上しない。

### 確定足の判定（R5）

`is_business_day()` は営業日か否かを返すだけで、その足が確定済みかは分からない。
場中の未確定足・引け後の配信待ち・休場を区別するため、基準日を決める時刻の契約を置く。

```python
@dataclass(frozen=True)
class BarStatus:
    symbol: str
    last_bar_session: date | None
    observed_at: datetime      # この足を観測した時刻
    is_final: bool             # 確定済みとみなせるか
    state: str                 # "fresh" | "stale" | "missing" | "provisional"
```

- `as_of_session` は「その実行時刻までに確定しているべき直近セッション」として決める
- 提供元で確定状態が分からない場合は、運用上の判定規約（引け後の待機時間）を記録する
- 営業日判定だけで足の確定を保証したとは扱わない

### データ更新とスキャンの連結

更新とスキャンを同じ `data_batch_id` の確定スナップショットで連結する。
部分更新の最中に入力が入れ替わらないようにするためである。
現行は16:00更新・16:20スキャンという時間差にのみ依存している。

### 判断時点の記録

`Signal` に `generated_at`（シグナルを作った時刻）と `data_as_of`（使ったデータの最終営業日）を
**別々に**保存する。`state != "fresh"` の銘柄は**新規候補から除外**し、理由を記録する。

**鮮度不足でも退出は止めない。** ただしこれは、古い日足から新しい売りシグナルを
自由に作ってよいという意味ではない。次の3つを別に扱う。

| 区分 | 鮮度不足時の扱い |
|---|---|
| 保有保護の退出（損切り・トレーリング） | 実行する |
| 既存注文の管理（取消・訂正） | 実行する |
| 新しい戦略シグナル（新規買い・シグナル売り） | 生成しない |

## 6. 段階B: 特徴量・ラベル・退出ポリシー（F05・F06・R1・R2）

### 保有状態

取得単価と数量だけでは、追加購入・部分決済・再起動を跨いだピーク価格・
ストップ発動状態を表せない。`Position.peak_price`（`src/data/database.py:162`）が
まさにその永続状態である。

```python
@dataclass(frozen=True)
class HoldingState:
    symbol: str
    entry_at: date
    avg_cost: float
    quantity: int
    peak_price: float      # 保有開始以降の最高値
    armed: bool            # ブレークイーブンが発動済みか
    sessions_held: int     # 経過営業日数
```

### 退出ポリシー

```python
@dataclass(frozen=True)
class ExitIntent:
    reason: str            # STOP_LINE / TRAILING / SIGNAL_SELL / TIME_LIMIT
    trigger_price: float | None   # 発動の基準となった価格。約定価格ではない
    order_type: str        # "MARKET" / "STOP"
```

`ExitPolicy.step(state, observation, config) -> (next_state, ExitIntent | None)` は
**その時点までに観測できた情報だけ**を受け取り、逐次的に状態を進める。
将来の足はまとめて受け取らない。

退出条件は `src/risk/manager.py:537-586` の `evaluate_exit()` と同じ構造にする。

1. 基準線 = `avg_cost × (1 + stop_loss_pct)`
2. ピーク時の含み益率が `breakeven_trigger_pct` 以上に達したら発動（`armed = True`）、
   基準線を `avg_cost` まで引き上げる
3. 発動後は `peak × (1 - trailing_stop_pct)` も基準にし、高い方（安全な方）を採る
4. 価格が基準線以下になったら退出意図を出す。理由は発動前が `STOP_LINE`、
   発動後が `TRAILING`
5. ルール由来の売りシグナルで `SIGNAL_SELL`
6. 最大保有営業日数に達したら `TIME_LIMIT`

**固定利確線は置かない。** 運用に存在しないためである。

### 日足内の順序の扱い

トレーリングには日足では解けない順序問題がある。ある日の高値がピークを更新して
基準線を引き上げ、同じ日の安値がその引き上がった線に触れる場合、
高値と安値のどちらが先に起きたかを日足から復元できない。

**既定は「当日の基準線を前営業日終了時点のピークで固定する」とする。**
当日の高値によるピーク更新は当日の終了後に反映する。これで日足内の順序に依存しなくなり、
未来のピークを遡ってストップへ使うことがなくなる。

あわせて「当日の高値を即座に反映する」楽観仮定でも計算し、両者の差を実行結果に記録する。
**この差が大きい戦略は、日中データを持つまで採用しない。**
悲観側へ寄せるだけでは順序問題は解決しないため、曖昧性を測って残す。

### 約定の分離

約定価格と控除は `execution.py` が一元的に決める。ポリシーは `trigger_price` までを返す。

| 条件 | 過去検証アダプタの仮定 |
|---|---|
| 基準線が寄りより上（ギャップダウン） | `min(open, trigger_price)` で約定 |
| 通常の日中到達 | `trigger_price` で約定 |
| `TIME_LIMIT` / `SIGNAL_SELL` | 翌営業日の寄りで成行約定 |
| 出来高制約・値幅制限・売買停止 | 未約定または部分約定として明示 |

エントリーも同じ扱いにする。Tの引けで判断し、T+1の寄りで `open × (1 + slip)` で約定する。
**満了日の終値で判断して同じ終値で約定する経路を作らない。**

### 学習ラベルの契約

第1版は `label` の定義を書いていなかった。次に固定する。

- **候補はバージョン固定のルールだけで生成する。** MLの予測を候補生成に使わない
- **退出は上記の退出ポリシーに従う。** MLは当面エントリー候補の選別に限定する
- `label = 1` は、仮定した執行と退出に基づく**コスト控除後の純収益が正**の場合。
  **0はlabel=0に含める**
- 未成熟・未約定・データ欠落は `label` を付けず、**別ステータス**にする。
  損失0として扱わない
- 最大保有期間は営業日数で数える

この契約は循環を避けるために必要である。`scores` に今回学習するML自身を含めると、
ラベルを作るためにそのMLの予測が要る循環が生じる。ルールのみで候補と売りシグナルを
決めることでこれを断つ。§8で比較する加重合成戦略も、**同じラベルの上で判断規則を
変えて評価する**のであって、ラベル生成をやり直すわけではない。

### RSIの端点仕様

| 条件 | 値 |
|---|---|
| `loss == 0` かつ `gain > 0` | 100 |
| `gain == 0` かつ `loss > 0` | 0 |
| 両方 0 | 50 |

### 欠損の扱い

日付インデックスを保持したまま `feature_valid` マスク列を返す**新しい関数**を追加する。
既存の `build_features()` は現在の挙動（`dropna` して返す）のまま残す。理由は§10に記す。

学習への採否はマスクで管理し、時間軸の連続性は市場系列側で保つ。

### イベント表

1行 = 1候補。

| 列 | 役割 |
|---|---|
| `event_id` | イベントの一意識別子 |
| `symbol` | 対象銘柄 |
| `decision_at` | 売買判断の時点（Tの引け） |
| `feature_as_of` | 特徴量に使った情報の最終時点 |
| `entry_at` | 想定した執行時点（T+1の寄り） |
| `label_end_at` | ラベル確定に使った最後の時点 |
| `label` / `status` | 予測対象と、未成熟・未約定・欠落の区分 |
| `net_return` | コスト控除後の純収益 |
| `exit_reason` | 退出意図の理由 |
| `sample_weight` | 一意性重み（fold内で再計算する。§7参照） |
| `dataset_id` / `feature_version` / `strategy_version` / `execution_model_version` | 再現用識別子 |

永続化は `data/datasets/<dataset_id>.csv.gz`。pandas標準で読み書きでき**依存追加が不要**である
（`requirements.txt` に pyarrow が無いため parquet は採らない）。

**書式を固定する。** 日時はタイムゾーンを明示、欠損値の表現、浮動小数点の出力精度、
列順、並び順、スキーマ版を固定する。`dataset_id` は**正規化した内容のハッシュ**とし、
取得日時を含む採取履歴IDとは別に持つ。同一内容なら同じ `dataset_id` になることを
テストで固定する。

## 7. 段階C: 学習・選択・最終評価の分離（F02・F03・F07・R6）

### 分割

fold境界は**全銘柄共通のカレンダー日付**で切る。行番号ではない。
`TimeSeriesSplit` を連結行に適用する現行方式では、銘柄Aの2026年が学習側・
銘柄Bの2024年が検証側に入る分割が成立する。

### purge と embargo

学習側から `label_end_at >= 検証開始日` のイベントを除外する（purge）。
片方向walk-forwardでは検証後の未来がそのfoldの学習に入らないため、
**後方embargoは既定で無効**とし、設定で有効化のみ可能にする。

### purgeだけでは塞がらない経路

purge以外にも学習側へ未来が入る経路があるため、次の4つに同じ制約を適用する。

1. **サンプル重み。** イベント表に一度だけ計算した一意性重みをそのまま各foldへ流すと、
   検証側イベントの終了時点が学習側の重みへ影響する
   （現行の `labeling.get_sample_weights()` は全期間の同時進行数から重みを作る）。
   **purge後の学習イベント集合で再計算する。**
2. **前処理。** 標準化・欠損補完・特徴選択・クラス比率推定・閾値・校正は
   **学習側だけでfitする。** 分割器だけを直しても全データfitならリークが残る。
3. **期間中の再学習。** バックテスト中の週次再学習にも同じ締切を適用する。
   その再学習時点までにラベルが観測可能になったイベントだけを使う。
   外側fold開始時に一度purgeするだけでは足りない。
4. **外側結果の使い方。** 外側成績を見て学習窓や戦略を選び、同じ成績を最終証拠として
   使わない。選択は内側で行い、選択後の未使用期間を別に確保する。

### 入れ子構造

- **外側fold** = 最終評価専用
- **内側fold** = early stopping・閾値選択・確率校正・学習窓選択・戦略選択

現行は early stopping に使った検証データでそのままCV指標を出しているため、
報告値が楽観に寄っている（`ml_model.py:147-160`）。

### 予測明細の保存

イベント単位で `event_id / evaluation_run_id / model_id / 予測時刻 / 生確率 /
校正後確率 / 出所fold / 予測用途` を保存する。これがあると**指標も売買判断も
後から再計算できる**ため、「AUC 0.5085が何を意味するか分からない」という現状が再発しない。

実績ラベルは予測時点では確定していない場合がある（shadowが該当する）。
**予測を先に保存し、満期後に実績ラベルを関連付ける更新規約**を置く。
これにより検証用予測と未確定の運用予測を同じテーブルで扱える。

### 比較対象（5つ固定）

定数確率 / 多数派予測 / ロジスティック回帰 / 小さいLightGBM / 現行LightGBM。
**深層モデルはこの段階では候補にしない。** 同じ入力・同じ分割で追加価値を示せるかを先に確かめる。

保存形式はモデルごとに定義する。LightGBM系はネイティブ形式、
それ以外は各々に適した形式でよく、**全モデルをLightGBM形式に押し込む必要はない**。

### 学習窓（F07）

`training_window_sessions` として明示パラメータ化し、実際の開始・終了日と銘柄ごとの採用件数を
保存する。拡大窓と一定期間の移動窓を**内側foldで**比較して選ぶ。
現行の「既定500行」は意図した選択ではなく `load_ohlcv` の既定値である。

### 記録する指標

- fold別・銘柄別・期間別の件数、正例率、除外件数（未成熟・未約定・欠落の内訳を含む）
- ROC-AUC、PR系指標、log loss、Brier と**定数モデルとの差**
- 予測確率のヒストグラムと校正曲線
- 取引に採用した上位群のコスト控除後成績
- 重要特徴の安定性

## 8. 段階D: ポートフォリオ walk-forward（F04・F08）

### 日次ループ（5フェーズ）

1. 前日までに決まった注文の執行（`execution.py`）
2. 保有と現金の更新（`portfolio.py`）
3. 退出ポリシーの逐次駆動と退出意図の処理
4. 日末評価（NAV記録）
5. 翌日の候補生成

**Tの終値の情報はT+1以降の注文にしか使えない。**

### 扱う条件

複数銘柄の資金競合、セクター上限、未約定、部分約定、出来高制約。
運用と同じ週次再学習スケジュールを再現する（§7の締切規約を適用する）。
現行は開始前に一度だけ学習し、テスト期間中は再学習しない（`engine.py:82-97`）。

### 実行条件のスナップショット

実行開始時に `run_id / strategy_version / config_hash / dataset_id / model_id /
code_version / execution_model_version` を保存する。
`config_hash` は同一性の確認に使えるが復元には使えないため、**設定JSONの実体も保存する**。
週次でモデルが変わる実行は `model_id` 一つでは表せないため、**実行内のモデル使用履歴を別に持つ**。

結果は最終リターンだけでなく、日次NAV・保有・注文候補・除外理由・予測確率まで辿れる形にする。

### 例外の扱い

推論例外が1件でも発生した実行には `degraded=true` を立て、比較とモデル昇格から除外する。

**これはv2の `walkforward.py` に最初からその挙動を持たせることで実現し、
`engine.py:160-161` の `except Exception: pass` は削除しない。**
旧エンジンの結果は§10のとおり旧エンジン由来として隔離され、比較にも昇格にも使わないため、
そこを直す必要が無い。旧エンジンに手を入れないという互換方針を優先する。

### 戦略バージョンの比較（F08）

**同じイベント表・同じラベルの上で、判断規則だけを変えて**3案を比較する。

1. 既存の加重合成（`rule_score * rule_weight + ml_score * ml_weight`）
2. 縮尺を明示したルール単独
3. ルールで候補を作り、MLで買う・見送るの順位を決める

**まず3を試す。**

期待値は `p × 平均利益 − (1−p) × 平均損失` で扱う。
**平均利益・平均損失はコスト控除後（`net_return` と同じ基準）で推定するため、
式の末尾でコストを再度引かない。** 利益側と損失側が非対称なら採用確率の境界は0.5にならない。
それぞれの推定値は学習期間だけで求める。

モデル失敗時は「ルール単独の定義済み戦略へ切替」または「新規候補生成を停止」の
どちらかを**設定として明示する**。現行は暗黙にルール重みだけが残る。

### paper経路の是正

paperは `stop_loss_check`（`src/services/trading.py:362-365`）だけでなく、
スキャン中の終値即時売買・時刻・注文の繰越を含めて設計する。

**過去の日足を再生するpaperと、現在の市場を観測するpaperは入力契約が違う。**
前者は日足による約定の近似であり、既存の翌朝9:05運用と同じ約定モデルとしては表示しない。

## 9. 段階E: 候補モデルの昇格と shadow（F09・R8）

学習成功はモデル更新ではなく**候補の生成**である。

- 候補は `models/candidates/<model_id>/` に置く
- 実体はバージョン別の不変ディレクトリへ保存し、**現行を指す小さな参照だけを原子的に更新する**
- 保存形式は pickle を廃し、LightGBMネイティブ形式 + JSONメタとする
- メタには `model_id` / 学習窓 / 銘柄集合 / ラベル定義 / 特徴量定義 / クラス比率 /
  fold別結果 / コード版 / 依存関係版 / `dataset_id` を保存する

### 昇格の契約

**今回の完了範囲は候補保存とshadowまでとし、自動昇格は無効とする。**
AUC等の採用数値をここで決める必要はない。

手動昇格を行う場合も、次を必須とする。

- 評価記録ID・判断者・理由・旧モデルID・切替日時を保存する
- `degraded` な実行、未評価、特徴量定義の不一致は**昇格不可**とする
- 途中失敗でファイルとDBの現行が食い違わないこと、再起動後に同じモデルへ復帰することを検査する

### 既存モデルの移行

第1版は既存 pickle を `models/current/` へ複製するとしたが、**これは行わない。**
v2では特徴量とラベルの契約が変わるため、旧モデルをv2の現行モデルとして扱えない。

- 旧モデル（`models/lgb_model.pkl`）は **`legacy` 用として保持する**
- **v2はモデル未昇格の状態から開始する**
- 旧モデルを比較用に変換する場合は、信頼済みファイルだけを対象とする明示的な変換手順を踏み、
  変換前後の予測一致と旧特徴量スキーマの維持を確認する。起動時の単なるコピーとは分ける

### shadow運用

同じ入力に対し現行と候補の判断を並行記録する。**候補は発注に繋がない。**
共有DBや設定の変更が現行判断へ影響しない構成にする。
差が何によって生じたかを、見送った候補の結果も含めて記録する。

## 10. 段階投入と後方互換（R3）

運用は止めない。

### `legacy` が意味する範囲

`config.yaml` に `strategy.engine_version: legacy | v2` を追加する。**既定は `legacy`**。

**ファイルを変更しなくても、依存先が変われば旧動作は維持されない。**
`engine.py:75` が `build_features()` を呼び、`engine.py:136` の
`if dt not in featured_df.index` が助走期間の除外を担っているため、
`build_features()` から `dropna` を外すとこのガードが無効化され、
NaN行が `compute_rule_score` と `predict_proba` へ流れる。
`src/strategy/signal.py` も同じ関数の戻り値を末尾2行だけ使う。

したがって:

- **既存の公開関数（`build_features()` / `build_training_set()`）は現在の挙動のまま残す**
- 日付保持・マスク付きの**新しいAPIを追加**し、v2経路だけがそれを使う
- 新APIを使う呼び出し側は `feature_valid == False` の行を明示的に扱う

### `engine_version` が切り替える3経路

| 対象 | `legacy` | `v2` |
|---|---|---|
| バックテストの実行主体 | `backtest/engine.py` | `backtest/walkforward.py` |
| 学習データの生成元 | `labeling.build_training_set` | `dataset.build_events` |
| CV分割 | `ml_model` 内の `TimeSeriesSplit` | `validation.calendar_folds` |

paper経路の執行仮定もこの設定で切り替わる（段階D後半）。
**この3経路の結線そのものは段階Fで行う。** 段階A〜Eは新しい経路を作るところまでで、
どちらを使うかを実運用へ繋ぐのは別の変更である。

### 変更の適用範囲

| 変更 | 適用範囲 |
|---|---|
| 取得境界・確定足判定・生値と調整値の分離 | **全経路**（legacy含む） |
| 日付保持API・イベント表・カレンダーCV・入れ子評価 | **v2のみ** |
| 執行仮定（T+1約定・ギャップ・未約定） | **v2バックテストとpaperのみ** |
| 実運用アダプタ | 段階Eのshadowまで導入しない |
| 発注経路 | 変更しない |

`legacy` は**旧評価方式へ戻す指定**であり、段階Aのデータ修正までは戻さない。
段階Aは全経路の共通土台であり、旧動作の一部ではなく欠陥の修正だからである。

### DBとファイル

- DBは加算マイグレーションのみ。追加列は全てnullable。既存44実行の記録は消さない
- `Signal.data_as_of` は**移行後に新規生成したシグナルに限定**して埋める。
  旧行の不明値を推測で補完しない
- 旧エンジンの過去結果は旧エンジン由来と分かる形で保管し、新エンジン結果と混ぜない
- 新データセットと候補モデルはDB外に置くため、**既存のバックアップ手順に
  新パス・参照整合・復元検証を追加する**

各段階の完了時点で既存テストが全て通ることは回帰の証拠の一つだが、
それだけでは新経路と切替の検証にならない。§13の完了条件を参照。

追加で固定する不変条件:

| ケース | 確認する不変条件 |
|---|---|
| Tの引け前に当日足を取得 | 日付がTでも、確定足として候補へ使わない |
| 最大保有期間まで足が届かない | 未成熟と区別し、満了契約どおり退出・ラベル確定 |

| 検証側イベントの終了時刻を変更 | そのfoldの学習側の重み・前処理・モデルが変わらない |
| 週次再学習 | 再学習時点で未確定のラベルが入らない |
| 同一データで複数戦略を評価 | 評価実行IDで予測・設定・成績を取り違えない |
| shadow直後でラベル未満期 | 予測を保存でき、満期後に正しいイベントへ実績を関連付ける |
| legacy/v2切替と再起動 | 宣言した互換範囲で同じ結果と正しいモデルへ復帰 |
| 昇格処理途中の失敗 | 現行モデル・DB・参照先が一貫して復元可能 |
| 候補モデルの障害 | 現行の発注・設定・特徴量入力へ副作用しない |

`labeling.py` は薄い層に縮小されるため専用テストファイルは作らないが、
公開関数を通した統合ケースを `test_dataset.py` に1つ含める。
薄いラッパーでも引数順・日付・マスク・設定の受け渡しは間違いうるためである。

**前回レビュー §10 の20ケースをそのまま落とすことはしない。**
20ケースには認証・プロファイル・ログなど今回スコープ外の項目が含まれるため、
該当ケースは別プランへ振り分ける。

## 13. 実施順

`dataset.py` がコスト控除後のラベルを作るため `execution.py` に依存する。
したがって執行の最小部分は段階Bと同時に必要である。

1. **契約確定** — 時刻、ラベル、退出状態、コスト、企業行動、新旧切替の範囲を決める
2. **A** — 取得境界、確定足判定、生値と調整値の分離、不変データスナップショット、入力の記録
3. **B前半** — 特徴量マスクと、最小の逐次ポリシー・約定シミュレーションを合成データで検証
4. **B後半** — 同じシミュレーションでイベント表・ラベルを作成
5. **C** — カレンダーCV、fold内の前処理・重み、予測明細、ベースライン
6. **D** — 複数銘柄・資金・部分約定・週次再学習を追加。単一イベントの正しさを維持
7. **E** — 候補管理とshadow。運用モデルの昇格は別の明示的判断

## 14. 完了条件

| 段階 | 完了条件 |
|---|---|
| A | 全シグナルが `data_as_of` を持ち、どの営業日の足から作られたか辿れる。確定していない足が新規候補として採用されない。1対2分割で株数と価格が整合し、分割だけでは評価額・現金・損益が増えない |
| B | 将来データを追加しても過去の特徴量が変わらない。未成熟ラベルを学習しない。ラベルの終了イベントが実行シミュレーションと一致する。当日の高値を遡ってストップへ使わない |
| C | **そのfoldの学習締切で固定されたモデルについて**、外側foldの値を変えてもモデル・前処理・重み・閾値が変わらない。予測明細から指標を再計算できる |
| D | Tの終値で買う条件が成立してもT+1以降にのみ約定する。degraded実行が比較から除外される。実行内のモデル使用履歴から週次再学習を辿れる |
| E | 学習失敗で現行モデルが失われない。shadowの候補が発注に繋がらない。昇格処理が途中で失敗しても現行が一貫して復元できる |

各段階の完了は「既存テスト + 該当段階の新規テスト + 移行テスト + 切替テスト」で確認する。
**テストの本数は合格基準にしない。**

段階Cの完了条件にある「外側foldの値を変えてもモデルが変わらない」は、
**その時点の学習締切で固定されたモデル**に対する条件である。
順次更新するwalk-forwardでは、ある時点の外側期間のデータが後の時点で既知の過去となり
学習に入ること自体は整合的であり、禁止しているのは
「その時点ではまだ未来だった情報が学習に影響すること」である。

**全体の合格条件は本設計では固定しない。** 「AUCが0.55を超えたら採用」「paperで1ヶ月成功したら合格」
といった一律基準は置かない。売買回数が少なければ期間を延ばし、比較の不確実性が大きければ保留する。
利益目標・許容ドローダウン・学習窓の最終値はユーザーの資金と運用目的に依存する未確定事項である。

## 15. スコープ外

- F10〜F15（リスク価格の鮮度、プロファイル適用の原子性、初期設定の保護、
  ログアウトとAPIトークン、ログのマスキング、DB制約と監査メタデータ）は別プランとする。
  §4の構造図に `PriceQuote` を含めないのはこのためである。日足の確定足判定（`BarStatus`）と
  運用リスク価格の鮮度（`PriceQuote`）は別物として扱う
- 深層モデルへの移行
- 日中データの導入（日足内の順序仮定の差が大きい戦略が出た場合に検討）
- モデルの自動昇格

## 16. リスクと未確定事項

1. **学習データ量が変わる。** 未成熟イベントの除外に加え、RSI修正・候補定義の変更・
   学習窓の変更が同時に効くため、増減の方向を事前に断定しない。
   段階Bの完了時点で**変更要因ごとの増減内訳**を測る。
2. **新旧エンジンの二重化期間がある。** 段階投入の要求上、`engine.py` と `walkforward.py` が
   並存する。段階Eの完了後に旧エンジンの廃止を別途判断する。
3. **改善後の成績は本設計では保証できない。** 是正は「測れる状態を作る」ことであり、
   MLが有効であることを示すものではない。段階Cの比較で追加価値が示せなければ、
   ルール単独運用を選ぶ判断もあり得る。
4. **日足内の順序は日足のままでは解消しない。** 悲観仮定と楽観仮定の差を測って
   記録するのみであり、差が大きい戦略の採否は日中データの導入判断に依存する。
