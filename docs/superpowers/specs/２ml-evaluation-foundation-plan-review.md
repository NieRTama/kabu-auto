# ML評価基盤の是正計画：設計レビュー

評価日：2026-09-10

対象：`2026-09-10-ml-evaluation-foundation-design.md`。以下の「計画L番号」は、今回共有された設計書の行番号です。実装や資料中のコマンドを実行する依頼ではなく、設計の評価として扱っています。

## 結論

**方向性は採用できます。ただし、今の文書をそのまま実装へ渡すのは勧めません。私の判定は「設計修正後に着手」です。**

日付を保持したイベント表、全銘柄共通の時間分割、purge、内側と外側の評価分離、候補モデルと運用モデルの分離は、前回指摘の原因に対応しています。深層モデルへの移行を後回しにし、評価可能性を先に整える目的も適切です。［根拠：計画L9–17、193–257、312–329］

残る問題は、**「同じ規則を使う」という方針と、その実装境界がまだ一致していないこと**です。退出・約定・ラベルの定義、新旧経路の切替、企業行動、時点管理を先に確定しないと、新しい基盤でも異なる前提の結果を比較する可能性があります。以下は計画本文の矛盾・未定義箇所に基づくレビュー判断です。

新しいリポジトリの `main @ 932f50f` とテスト一式は今回は提供されていません。「最新コードで全件現存」「単体テストなし」は設計書内の調査報告として扱い、こちらで追認した事実とはしません。前回共有ソースとの照合は補助に留めています。［根拠：計画L21–47、今回の提供資料］

### R1：ExitPolicyは実際の約定価格を決める役ではない

計画では `ExitPolicy.evaluate(entry, bars, scores)` が退出時点と約定価格を返し、ラベル・バックテスト・運用の3者が呼びます。一方、`execution.py` も「いつ・いくらで約定させるか」を決めます。責任が重複しています。［計画L88–95、138–175］

さらに、将来の日足をまとめて受け取る関数は過去検証では使えますが、そのままでは将来足のない実運用のインターフェースになりません。「運用ではその時点までの足だけを渡す」なら、その契約と途中状態の保存が必要です。取得単価・数量だけでは、追加購入、部分決済、再起動を跨いだピーク価格やストップ発動状態も表しきれません。［計画L149–158、273］

**私なら次の3層に分けます。**

| 層 | 入力 | 出力 |
|---|---|---|
| 共通ポリシー | 現在の保有状態、その時点で観測できる価格・スコア、固定設定 | 次の状態、退出意図、発動理由 |
| 過去検証アダプター | 退出意図、注文条件、利用可能な日足 | 仮定に基づく約定・未約定・部分約定 |
| 実運用アダプター | 退出意図、実際の市場情報 | 注文の実行と、証券会社から確認した約定 |

ラベルとバックテストは同じ過去検証アダプターで共通ポリシーを逐次再生します。運用は実際に観測した情報と約定結果を渡します。`exit_price`をポリシーから外し、`trigger_price`等が必要なら約定価格と明確に区別します。これは設計提案です。

日足の「上下バリアが同日に到達したら損切り」は一つの仮定として妥当ですが、トレーリングには追加の順序問題があります。その日のhighでストップを引き上げた後、先に発生した可能性があるlowで約定したことにしてはいけません。日足しかないなら、前日までのピークで当日の線を固定するか、日中経路の複数仮定を比較して曖昧性を結果に記録します。「3者共通の悲観規約」だけでは、この問題を解決したことにはなりません。［計画L164–175からの設計上の指摘］

受入テストは、単なるpolicyとbacktestの相互一致に加え、手計算で決めた価格経路の期待値、将来足を渡さない運用呼出し、同じ足の再処理、再起動後の状態復元を含めます。同じ実装を共有していれば、同じバグでも両者は一致してしまうためです。

### R2：学習ラベルの契約を一つに決める

イベント表には `label / net_return` がありますが、`label=1`の条件が定義されていません。利益バリア到達、コスト後損益が正、特定期間後の上昇は別の目的です。時間バリアまでデータが揃った場合の退出価格・タイミングも未定義です。［計画L145–173、193–207］

また、`scores`には `combined_score` を渡す一方、ラベル作成時は空辞書でもよいとしています。ラベルだけ売りシグナルを無視した場合、関数が同じでも退出結果の意味は運用と一致しません。予測対象を補助ラベルとして意図的に変えることはできますが、その場合は「運用と同じ取引結果を学ぶ」とは区別して記載すべきです。［計画L158、175、393］

`combined_score`に今回学習するML自身を含めるなら、ラベルを作るためにそのMLの予測が必要になる循環もあります。既存モデルから作るなら、そのモデルの学習締切と予測の来歴が必要です。

私なら初期版は次の契約に固定します。

- 候補はバージョン固定したルールだけで生成する。
- 退出の売りシグナルも固定ルール由来にする。MLは最初はエントリー候補の選別に限定する。
- `label=1`は仮定した執行・退出に基づくコスト後損益が正の場合。0損益は0に含めるなど、境界を明記する。
- 未成熟、未約定、データ欠落は「損失0」とせず別ステータスにする。
- 最大保有期間の数え方、満了時の注文時刻と約定時刻を明記する。満了日の確定終値で判断して同じ終値に約定する経路を作らない。
- 固定利確を使うなら、そのバリア値と理由コードを定義する。使わないなら「利確線との同時到達」という規約を対象に合わせて書き直す。

すべて提案です。現行契約を維持したい場合も、同じ項目を明文化すれば別の選択ができます。

コストについても、§6は `net_return` を控除後とし、§8の期待値式は末尾で再びコストを引きます。平均利益・平均損失をgrossで推定するのかnetで推定するのか決めてください。net損益から平均を作り、さらにコストを引くと二重控除になります。［計画L160–173、204、301–302］

### R3：`legacy`への切替だけでは元の動作へ戻らない

`engine_version`の切替対象はバックテスト主体・データ生成・CVの3点だけです。しかし共有する `build_features()` の戻り値を変更し、`labeling.py`も新policyを呼ぶ層に縮小します。旧エンジンのファイルを変更しなくても、その依存先が変われば旧動作は維持されません。［計画L73–78、187–191、335–345］

前回共有ソースの `signal.generate()` は `build_features()` の結果をそのままルール計算に渡し、ルール計算は末尾2行を使っています。dropnaをなくした後の `feature_valid=False` を呼出し側が扱わなければ、不正な最新行で判定する経路になります。この点は最新リポジトリでも呼出し元を確認してください。［補助根拠：前回共有 `src/strategy/signal.py`:24–35・79–80］

文書上でも次が矛盾しています。

- 旧 `engine.py` は無改造で残す一方、同ファイルの `except Exception: pass` を廃止する。［L78、287–288、345］
- 段階Bで運用も共通policyを呼ぶ一方、発注経路はEのshadowまで無改造とする。［L149–175、345］
- paper経路を修正する一方、切替対象の3点にはpaperが含まれない。［L307–310、337–345］

私なら、既存の公開関数を互換ラッパーとして残し、日付保持の新APIを追加します。同時に「全経路へ適用する日付修正」「v2だけに適用する学習・評価変更」「paperでのみ有効にする執行変更」を表で固定します。`legacy`は旧評価方式に戻すための指定なのか、売買判断まで完全に戻す指定なのかを分けてください。

paperは `stop_loss_check` だけでなく、スキャン中の終値即時売買、時計、注文の繰越も含めて設計します。過去の日足を再生するpaperと、現在の市場を観測するpaperは入力契約が違います。日足寄付の近似を、既存の翌朝9:05運用と同じ約定モデルとして表示しない方針を明記するのがよいです。［計画L307–310、前回レビュー§6］

### R4：企業行動の先送りは、Dの目的に制約を付ける必要がある

計画は調整済みOHLCを使い続け、分割等のイベント保存をDの完了後へ送ります。一方、Dは現金・株数・出来高・複数銘柄の資金競合まで評価します。データを凍結して再現できても、価格と株数の意味のずれは残ります。［計画L127–134、271–283、407］

yfinanceの `auto_adjust=True` はOHLCを調整する指定です。履歴価格に基づき当時の単元購入可否を検証する場合、調整価格をそのまま当時の約定可能価格として扱う問題は、取得日時の保存では解消しません。［外部根拠：E1］

説明例として、当時1株1,000円、予算6万円、100株単位なら購入できません。後の1対2分割で過去価格が500円に調整され、その価格で100株購入をシミュレートすると、購入可能という別の結果になります。これは実銘柄のデータではなく、問題を示す計算例です。

私なら、Dへ進む前に原価格・分割情報・調整係数を確保します。最小テストは「100株×1,000円が分割後200株×500円になり、分割だけでは評価額・現金・損益が増えない」です。配当も現金と調整価格で重複させない契約にします。

工数上ここを後回しにするなら、Dの成果を「調整系列での研究用比較」と限定し、実資金の数量・資金競合検証やモデル本番昇格の根拠には使わない、と完了条件へ追記します。問題なのは先送り自体ではなく、先送りしたまま何を検証できたと呼ぶかです。

### R5：fresh判定には日付と情報の確定時刻が必要

`end + 1日`は当日足を取得対象に含める方向として合っています。ただし `is_business_day()` は営業日かどうかを判定するだけです。場中の未確定足、引け後の配信待ち、休場日を区別するために、基準日を決める時刻の契約が必要です。［計画L99–118、前回共有 `src/core/market_calendar.py`、E1］

私なら、`as_of_session`を「その実行時刻までに確定しているべき直近セッション」とし、`observed_at / available_at / is_final`または同等の明示的な扱いを加えます。提供元で確定状態を取れなければ、運用上の判定規約を記録します。営業日判定だけで足の確定を保証したとは扱いません。

また、取得関数の内部と呼出し側の双方で1日足すことがないよう、終了日の公開仕様を「含む／含まない」のどちらかに固定します。更新→スキャンは、同じ `data_batch_id`の確定スナップショットで連結します。部分更新の最中に入力が入れ替わらないようにします。これらは追加提案です。

「鮮度不足でも退出を止めない」という方針は維持します。ただし、それは古い日足から新しい売りシグナルを自由に作ってよいという意味ではありません。保有保護の退出、既存注文の管理、新しい戦略シグナルを別に扱うと誤解を防げます。［計画L117–125］

### R6：purge以外にも学習側へ未来が入る経路を塞ぐ

全銘柄共通の日付分割、`label_end_at`によるpurge、片方向walk-forwardで後方embargoを既定無効にする方針は維持してよいです。［計画L214–232］

不足しているのは、その制約をどこまで適用するかです。

1. **サンプル重み**：イベント表に一度だけ計算した一意性重みを入れ、そのまま各foldへ流すと、検証側イベントの終了時点が学習側重みへ影響する場合があります。purge後の学習イベント集合で再計算する契約を加えます。［計画L206、222、382。前回共有 `labeling.py`:80–101からの指摘］
2. **前処理**：ロジスティック回帰用の標準化・欠損補完、特徴選択、クラス比率推定、閾値、校正も学習側だけでfitします。分割器だけを直してもここが全データfitならリークが残ります。［計画L226–257、外部根拠E2］
3. **週次再学習**：再学習時点までにラベルが観測可能になったイベントだけを採用します。外側fold開始時にpurgeするだけでなく、期間中の各再学習にも同じカットオフを適用します。［計画L273–275］
4. **外側結果の使い方**：外側成績を見て学習窓や戦略を選び、同じ成績を最終証明として使わないことを明記します。選択は内側で行うか、選択後の未使用期間を別に確保します。［計画L228–248、E2・E3］

外側foldの値を変えてもモデルが変わらないというテストは、**そのfoldの学習締切で固定されたモデル**に対する条件としてください。順次更新するwalk-forwardでは、ある時点の外側期間のデータが、後の時点で既知の過去となり学習に入ること自体は整合的です。その時点ではまだ未来だった情報だけが学習に影響しないことを検査します。これは前回レビューの同じテスト表現にも必要な補足です。［計画L394、前回レビュー§10］

### R7：取得日時とIDだけでは再現性は成立しない

§5は取得時点を `dataset_id` に記録すればデータ改訂との差を分離できるとしていますが、取得日時だけではその時点の入力値を復元できません。イベントCSVの保存とSHA256は進歩ですが、イベント表の列には実際の特徴量や元OHLCVの保存先が明示されていません。［計画L132–134、193–210、354–362］

私なら最小限、次を結び付けます。

| 記録 | 追加したい内容 |
|---|---|
| 入力スナップショット | 実際に使用したOHLCV・企業行動・銘柄集合の不変ファイルと内容ハッシュ |
| イベント | `event_id`、特徴量実体または再構築可能な参照、ラベル版、コスト・執行モデル版 |
| 評価実行 | `evaluation_run_id`、設定JSON実体、fold境界、モデル選択手順、コード版 |
| 予測 | `event_id`、評価実行ID、モデルID、予測時刻、生確率、校正後確率、内外fold、予測用途 |
| 再学習履歴 | 学習締切、モデルID、実際に使い始めた時刻・期間 |
| 売買判断 | ルールスコア、閾値、候補順位、採否、除外理由、該当予測・モデル・設定への参照 |

週次でモデルが変わる実行を `BacktestRun.model_id` 一つだけでは表しきれません。実行内の使用履歴を別に持たせます。また `config_hash` は設定の同一性確認には使えますが、設定実体がなければ復元には使えません。［計画L274、279–283、356–360からの指摘］

shadowでは予測時点に `y_true` はまだ確定していません。予測を先に保存し、成熟後に実績ラベルを関連付ける更新規則が必要です。これを明記すると、検証用予測と未確定の運用予測を同じテーブルで取り違えずに済みます。［計画L236–238、328–329、357］

CSV.gzの採用には反対しません。日時のタイムゾーン、型、欠損値、浮動小数点の出力精度、並び順、スキーマ版を固定してください。`dataset_id`を内容由来にするなら、取得日時を含む採取履歴IDと分けると「同一データなら同じID」というテストが明確になります。圧縮ファイルのバイト列を使うか、正規化した内容を使うかも決めます。［計画L209–210、376への提案］

### R8：モデル昇格は、保存先を分けただけでは完成しない

候補を分ける方針は適切です。ただし「評価を通るまでcurrentを保持する」に対して、誰が何を見て切り替えるかが定義されていません。§13のE完了条件は学習失敗時の保持とshadowの非発注だけで、昇格の契約としては不足しています。［計画L314–329、396–400］

AUC等の一律の採用数値を今決める必要はありません。私なら、今回の完了範囲を「候補保存とshadowまで。自動昇格は無効」と明示します。手動昇格を含めるなら、評価記録ID・判断者・理由・旧モデルID・切替日時を保存し、`degraded`、未評価、特徴量不一致は昇格不可とします。

移行にも追記が必要です。既存pickleとJSONを `models/current/` に複製しても、LightGBMネイティブ形式には変わりません。また特徴量やラベルの契約が変わるので、旧モデルをv2現行モデルとしてそのまま扱えるとは限りません。［計画L317–324］

私なら旧モデルを `legacy`用として保持し、v2はモデル未昇格の状態から開始します。旧モデルを比較用に変換する場合は、信頼済みファイルだけを対象とする明示的な変換手順、変換前後の予測一致、旧特徴量スキーマの維持を確認します。起動時の単なるコピーとは分けます。

実体はバージョン別の不変ディレクトリへ保存し、切替先を示す小さな参照だけを原子的に更新する案を勧めます。途中失敗時にファイルとDBのcurrentが食い違わないこと、再起動後に同じモデルへ復帰することも検査します。shadow側には発注依存を渡さず、共有DBや設定の変更が現行判断へ影響しない構成にします。

## 2. 段階ごとの進め方を少し変えたい

現在はBでラベル用policyを完成させ、Cで学習評価、その後Dで執行を作ります。しかしBのコスト後ラベルは `execution.py` に依存するので、執行の最小部分はB以前かBと同時に必要です。責務表でも `dataset.py` の依存先に `execution.py` がなく、本文のコスト計算と対応していません。［計画L88–95、160–162、259以降］

私なら次の順にします。

1. **契約確定**：時刻、ラベル、退出状態、コスト、企業行動、新旧切替を決める。
2. **A**：取得境界、確定足判定、不変データバッチ、入力の記録。
3. **B前半**：特徴量マスクと最小の逐次policy・約定シミュレーションを合成データで検証。
4. **B後半**：同じシミュレーションからイベント・ラベルを作成。
5. **C**：カレンダーCV、各fold内の前処理・重み、予測明細、ベースライン。
6. **D**：複数銘柄、資金、部分約定、週次再学習を追加。単一イベントの正しさを維持。
7. **E**：候補管理とshadow。運用モデルの昇格は別の明示的判断。

これは計画の骨格を維持した依存関係の調整です。作業を広げるための追加段階ではありません。

## 3. テストと完了条件に追記したいこと

「既存テスト60本超がすべて通る」は回帰の証拠の一つですが、それだけでは新経路や切替の検証にはなりません。計画には新規テスト案が既にあるため、完了条件を「既存テスト＋該当段階の新規テスト＋移行／切替テスト」と書き換えれば整います。テストの数自体は合格基準にしない方が明確です。［計画L350、364–396］

私なら以下を追加します。

| ケース | 確認する不変条件 |
|---|---|
| Tの引け前に当日足を取得 | 日付がTでも確定足として候補へ使わない |
| 設定した最大保有期間まで足が揃う | 未成熟と区別し、満了契約どおり退出・ラベル確定 |
| 同日にhigh更新とlow到達 | 未来のピークを遡ってストップへ使用しない |
| 推論時の最新行がfeature_valid=false | 古い行への無言の置換やNaN判定をしない |
| 検証側イベントの終了時刻を変更 | そのfoldの学習側の重み・前処理・モデルが変わらない |
| 週次再学習 | 再学習時点で未確定のラベルが入らない |
| 1対2分割 | 株数と価格が整合し、分割だけで利益・現金が増えない |
| 同一データで複数戦略を評価 | 評価実行IDで予測・設定・候補を取り違えない |
| shadow直後でラベル未成熟 | 予測が保存でき、成熟後に正しいイベントへ実績を関連付ける |
| legacy/v2切替と再起動 | 宣言した互換範囲で同じ結果と正しいモデルへ復帰 |
| 昇格処理途中の失敗 | 現行モデル・DB・参照先が一貫して復元可能 |
| 候補モデルの障害 | 現行の発注・設定・特徴量入力へ副作用がない |

`labeling.py`のためだけにテストファイルを増やす必要はありません。ただし薄いラッパーでも列順、日付、マスク、設定の引渡しは間違えられます。`test_dataset.py`等から公開関数を通す統合ケースを一つ含めれば十分です。［計画L381–382への提案］

前回レビュー§10の20ケースには、今回スコープ外の認証・プロファイル・ログ等も含まれます。「20ケースをそのまま落とす」はスコープ宣言と合っていません。各ケースを「今回」「別プラン」に振り分けてください。［計画L384、404–405、前回レビュー§10］

## 4. 文書の軽微な修正候補

- **F10とpaperの位置付け**：前回レビューはリアルタイム価格優先を認識した上で、鮮度・由来が失われる問題を指摘しています。またpaperの終値執行・損切りは前回レビュー§6で扱っています。「前半修正済み」「レビューにない追加」という説明は、今回の新規差分を誤認しやすいため整理を勧めます。［計画L42–53、前回レビュー§6・§7］
- **テストゼロの断定**：専用の単体テストファイルがないことと、他ファイルの統合・回帰テストでも一切検証していないことは別です。後者まで調査したなら調査方法を添え、そうでなければ「専用テスト未確認／未整備」とします。こちらでは最新テストを確認していません。［計画L45–47、366］
- **サンプル数減少の断定**：未成熟除外だけなら減少しますが、同時にRSI修正、候補定義、学習窓を変えるので、変更全体で19,458から必ず減るとは言い切れません。段階Bで増減内訳を測る表現が正確です。［計画L181–207、247–249、412–414］
- **BacktestRunの表現**：「閾値とコストしか持たない」ではなく、「完全な実行設定・モデル・入力データの来歴が不足」と書く方が正確です。前回共有スキーマには期間、資金、成績等もあります。［計画L281、前回共有 `src/data/database.py`:177以降］
- **PriceQuoteの範囲**：構造図にはPriceQuoteがありますが、F10は対象外です。日足のDataFreshnessと、運用リスク価格のPriceQuoteを区別し、後者を今回扱うなら範囲へ明記します。［計画L5、83、106–113、404］
- **モデル形式**：比較対象にロジスティック回帰がある一方、保存形式はLightGBMネイティブに統一されています。比較用モデルの保存・再読込方法も定義します。LightGBM形式に全モデルを押し込む必要はありません。［計画L242、321］
- **旧Signalのdata_as_of**：新列nullableで旧行を残すのに「全シグナルがdata_as_ofを持つ」は文字どおりには満たせません。「移行後に新規生成するシグナル」に限定し、旧行の不明値を偽って補完しない方針を加えます。［計画L359、392］
- **バックアップ範囲**：DB外に新データセットと候補モデルを保存するため、既存のバックアップ手順に新パス・参照整合・復元検証を追加する作業を明示します。［計画L209、316、362への提案］
